# 候选结果与结算（outcomes）

这份文档说明一条规则"要产出什么"和"要付什么代价"：`effects` 与 `outcomes` 两种写法、多个结果之间怎么轮换、规则级固定成本（`source_cost` / `catalyst_cost`）、消耗类效果与成本的关系，以及一组掉落物究竟怎么扣、怎么产出、没转化成功时东西去哪了。

单个效果的参数（`spawn_entity` 生成什么、`place_block` 怎么摆等）见 [效果](04-effects.md)；周围产物上限、每刻检查次数等服务器参数见 [服务端配置](07-server-config.md)；"要不要转化"由条件决定，见 [条件配置](03-conditions.md)。

## 结果方案：写 `effects` 还是 `outcomes`

规则必须回答"转化出什么"，有两种写法：

| 写法 | 含义 | 结果数量 |
|---|---|---|
| 只写 `effects` | 这条规则只有一个结果，相当于隐式写了一个 `id` 为 `default` 的候选结果 | 1 个 |
| 写 `outcomes` | 一条规则里列出多个候选结果，每一组按 `combination` 挑一个执行 | 1 个以上 |

- 两个都不写：规则被拒载（至少要有一个结果）。
- 两个同时写：规则被拒载（二选一）。想把单结果改成多结果，就是把原来的 `effects` 内容搬进 `outcomes` 里，作为某个候选结果的 `effects`。
- 只写 `effects` 时不用写结果 id，隐式结果的 id 固定是 `default`；写 `outcomes` 时每个候选结果都必须自己写 `id`。
- 一个候选结果的 `effects` 不能是空数组；一个结果里的多个效果会在**同一组**里一起执行。

### 候选结果字段

| 字段 | 含义 | 取值 | 默认 | 说明 |
|---|---|---|---|---|
| `id` | 这个结果的名字 | 非空字符串 | 无（必填） | 同一条规则内不能重复；只写 `effects` 时隐式结果叫 `default` |
| `effects` | 这个结果要执行的动作 | 效果数组 | 无（必填，不能为空） | 效果种类与参数见 [效果](04-effects.md) |
| `safe_spawn` | 生成生物时是否挑安全位置 | `true` / `false` | `false` | 只影响 `spawn_entity` 生成生物的那种产出 |
| `fill_origin` | 放方块时是否允许填到触发位置本身 | `true` / `false` | `true` | 只影响 `place_block` |

候选结果对象里只认上面这四个字段，多写一个都会被拒载。

### `safe_spawn` 改变什么

- `false`（默认）：不挑位置，生物直接出现在掉落物原来的位置（水平方向带一点极小的随机偏移）。
- `true`：以触发位置为中心，在水平 ±2 格、上下各 2 格的范围（5×5×5，共 125 个候选格）内，按"离触发点由近到远"的顺序找第一个能站的安全位置：在世界边界内、这种生物按原版规则可以生成、碰撞箱里没有方块、脚部和头部不在火/岩浆/仙人掌里。命中时生物出现在那一格的中心。
- 全部候选都不安全时，退回触发位置附近生成（带一点随机偏移），不会因为挑不到位置就不生成。
- 只对生成**生物**生效：生成物品、生成经验不看这个开关。
- 挑位置是分帧做的：每刻最多检查若干个候选格（次数由服务器参数控制），一批没挑完会在下一刻接着挑，所以生物可能比物品晚一点出现。

### `fill_origin` 改变什么

- `true`（默认）：`place_block` 的填充候选里包含触发位置所在的那一格。
- `false`：把触发位置本身从填充候选里去掉，其余候选的位置与顺序不变。适合"不想让方块正好压在掉落物原来那格"的场景。
- 只对 `place_block` 生效；同一条规则的不同候选结果可以各写各的。

### 一个双结果示例

保存为 `config/itemdespawntowhat/rules/myrules/chicken_two_forms.json`：

```json
{
  "id": "myrules:chicken_two_forms",
  "source": {
    "items": [
      "minecraft:chicken"
    ]
  },
  "trigger_after_seconds": 300,
  "source_cost": {
    "minecraft:chicken": 1
  },
  "combination": "round_robin",
  "outcomes": [
    {
      "id": "rotten_flesh",
      "effects": [
        {
          "type": "itemdespawntowhat:spawn_entity",
          "variant": "item",
          "item": "minecraft:rotten_flesh",
          "count": 1
        }
      ]
    },
    {
      "id": "chick",
      "effects": [
        {
          "type": "itemdespawntowhat:spawn_entity",
          "variant": "entity",
          "entity": "minecraft:chicken",
          "age": -24000,
          "count": 1
        }
      ],
      "safe_spawn": true
    }
  ],
  "schema_version": 1
}
```

配完会发生什么：鸡肉到时间后要么变腐肉，要么孵出幼年鸡（`age: -24000` 表示幼年）；孵出的那只不会再卡在墙里，因为第二个结果开了 `safe_spawn`。

## 组合模式 `combination`

| 取值 | 含义 | 默认 |
|---|---|---|
| `round_robin` | 轮流：这一组用一个结果，下一组换一个 | ✔ |
| `priority` | 固定优先级：每次都从声明顺序的第一个候选开始，谁先能开出一组就用谁 | |

大小写不敏感（`round_robin` 或 `ROUND_ROBIN` 都行）；写其它值规则会被拒载。只有一条规则里存在两个以上候选结果时，这个字段才有实际作用。

### `round_robin`："轮到谁"是怎么记的

- 轮转位置不记在掉落物身上，而是按**规则 id + 维度**记在世界存档里：同一条规则在同一维度下的所有掉落物共用同一个位置。
- 每开出一组就往前走一位。所以一次消失的整堆掉落物如果开出 3 组，就会依次用掉 3 个候选结果。
- 这个位置会跟着存档保存：服务器重启、退出再进入都接着上次继续；换维度各算各的。
- 起点是第一个候选结果；候选结构发生变化（改动结果 id、`safe_spawn`/`fill_origin`、或效果的组成与参数）后，轮转位置会重新从第一个开始。
- 轮转只会挑"当前还能再开出一组"的候选（比如周围同类产物已达上限的候选会被跳过），所以实际拿到的未必严格是声明顺序的下一个。

### `priority`：结果有明确先后

- 每开一组都从声明顺序的第一个候选往下找，用第一个能开出一组的。
- 只要前一个候选还能开组，后面的候选就永远不会被用到——写 `priority` 相当于给结果排了先后，后面的当成"前面不可用时的备选"。

### 同一个掉落物每次拿到哪个结果

以上面那份双结果规则为例（`source_cost` 是每 1 个鸡肉一组；这里假设这条规则还从没轮转过）：

- 掉落 1 个鸡肉：开出第 1 组，用 `rotten_flesh` → 得到腐肉；轮转位置移到 `chick`。
- 之后再掉落 1 个鸡肉：从 `chick` 开始 → 孵出幼年鸡；位置转回 `rotten_flesh`。
- 一次掉落 5 个鸡肉（同堆叠）：整堆被拆成 5 组，依次得到 腐肉、鸡、腐肉、鸡、腐肉。
- 把 `combination` 改成 `priority`：每次都出腐肉；只有腐肉那条路走不通时（例如产物已达上限）才会轮到孵鸡。

## 每组要付多少：固定成本与消耗

一条规则可以声明"每开一组要付多少"的**规则级固定成本**（`source_cost`、`catalyst_cost`），也可以用**消耗类效果**（`consume_source`、`consume_catalyst`、`consume_fluid`）在开组时扣东西。两种写法效果重叠，但同类东西只能选一种：`source_cost` 与 `consume_source` 不能同时声明，`catalyst_cost` 与 `consume_catalyst` 不能同时声明，否则会被拒载（避免同一份东西被记两次账）。

### `source_cost`：每组的源物品成本

写法是一个"源物品引用 → 正整数"的对象，数量就是每组要扣多少个：

```json
{
  "source_cost": { "minecraft:chicken": 1 }
}
```

```json
{
  "source_cost": { "#minecraft:saplings": 1 }
}
```

- 键必须是 `source.items` 里出现过的条目，写法要和 `source.items` 一致（那里写物品就写物品，写 `#标签` 就写 `#标签`）；数量必须是正整数。违反任一条，规则会被拒载。
- 可以同时写多个条目，例如 `{ "minecraft:egg": 2, "#minecraft:saplings": 1 }`。具体扣多少由**当前这堆源物品**决定：先找与该物品完全相同的条目，没有就按 `source.items` 的声明顺序找第一个命中的 `#标签` 条目。
- 语义是"每开一组扣这么多"，与整堆大小无关：写 2 表示每 2 个源物品开一组、产出一次；一次消失 5 个只会开 2 组，剩 1 个返还。

### `catalyst_cost`：每组的催化剂成本

| 字段 | 含义 | 取值 | 默认 | 说明 |
|---|---|---|---|---|
| `items` | 需要哪些催化剂 | 物品或 `#标签` 的数组 | 无（必填，不能为空） | 在触发位置半径内凑齐 |
| `count` | 每种催化剂要扣的数量 | 1–64 | 1 | 被 `counts` 单独指定的种类除外 |
| `radius` | 在触发位置周围多大范围内找催化剂 | 1–8（格） | 1 | |
| `counts` | 为某几种催化剂单独指定数量 | `{ "引用": 数量 }` | `{}`（都用 `count`） | 键必须是 `items` 里已有的条目 |

- 催化剂成本只认这四个字段，而且必须是对象：`items` 为空、`counts` 引用了没写在 `items` 里的东西、数量越界都会被拒载。写 `chance`、`conditions`、`delay_ticks` 之类同样会被拒载——规则级成本没有"有概率地付"和"等一会儿再付"。
- `items` 里每个引用**分别**付够自己的数量：列了两种催化剂就两种各付，不是合起来只付一种。
- 支付时机是**每开一组之前先付**，所以是"按组付"，不是整堆一次性付清。
- 半径内数量不够时：这一组不开——源物品成本不扣、这个结果不产出，剩下的部分最后作为返还物回到世界。
- 同一格范围内的物品会被反复利用，多个引用可以共享同一堆库存。

### 消耗类效果与规则级成本的对应关系

| 消耗效果 | 扣什么 | 与规则级成本的对应关系 |
|---|---|---|
| `consume_source` | 每组的源物品 | 对应 `source_cost`，两者只能选一个 |
| `consume_catalyst` | 每组的催化剂（触发位置半径内） | 对应 `catalyst_cost`，两者只能选一个 |
| `consume_fluid` | 触发位置附近的流体 | 没有规则级对应字段，只能写成效果 |

- 效果的参数、通用字段（`delay_ticks`、`chance`、`conditions`）见 [效果](04-effects.md)。
- 同一种消耗效果在同一条规则里（顶层 `effects` 与各候选结果的 `effects` 合并计算）只能声明一次，重复声明会被拒载。
- 写在某个候选结果里的消耗效果，只在这个结果被选中、这一组被开出时才发生。

### 什么都没写时的隐式消耗

- 一条规则如果既没有任何消耗类效果、也没有 `source_cost`/`catalyst_cost`，按默认语义处理：**每开一组扣 1 个源物品**。也就是"1 个源物品换 1 次产出"。
- 只要显式声明了任何一种消耗效果或规则级成本，隐式的那 1 个就不再叠加：不会出现"写了一个消耗还要再多扣一个"的情况。内置示例都是显式写法，效果与默认语义一致。
- 一个容易踩的坑：只声明 `consume_catalyst`（或只声明 `consume_fluid`），却既不写 `consume_source` 也不写 `source_cost`——此时源物品**不参与分组**，整堆只算一组，催化剂/流体也只按一组支付。想让整堆按个数一组一组转化，就要写 `source_cost` 或 `consume_source`。

## 整组结算与返还

掉落物被规则选中后，它的整堆先离开世界进入结算，结算按下面几步走：

1. **算组数**：组数 = 整堆数量 ÷ 每组源物品成本，向下取整；每组成本为 0（不消耗源物品）时整堆只算 1 组。实际开出的组数还可能被容纳上限压低。
2. **逐组开组**：每一组先支付催化剂（配了 `catalyst_cost` 或 `consume_catalyst` 时），再扣掉本组的源物品，然后执行这个结果里的全部效果。任何一步付不起，这一组就不开。
3. **返还剩下的**：整堆里没有用到的部分作为掉落物重新回到世界（落在触发位置附近，位置不好会向上或在高空生成后自然落回）。
4. **返还物不会再被转化**：返还回来的源物品带永久保护，既不会再次参与转化，也不会再把这一堆拆回去，避免"返还—再次转化—再返还"的死循环。保护只在这一次结算产生的返还物上，不影响之后再丢进来的新掉落物。

关于"只算真实成功量"：

- 产出账目只记录**真正生效**的部分。一组里某个效果因为概率落空、自身条件不满足或执行失败而没有产出时，这一组不会被记为成功产出；"计划要产出多少"和"实际成功多少"是两回事。
- 成本一旦扣掉就不会因为产出没成功而退回：概率落空同样要付这一组的源物品成本，属于"付费重试"而不是免费重试。
- 反过来，没开成组的成本完全没有发生：那部分源物品一直留在整堆里，最后作为返还物回来。

中断与恢复：

- 退出世界、服务器关闭或目标维度卸载时，还没交付的部分不会凭空消失：已经扣掉的成本照实记着，尚未返还的源物品会在该维度重新加载后补上（位置优先用原来的触发位置；旧存档里没有位置信息时，退回该维度出生点附近）。
- 恢复阶段只做"把该返还的源物品交回去"这一件事：不会重跑规则，也不会重新执行已经派发出去的效果。已经派发、还没回执的产出不会被再算成"应该返还的源物品"，源物品与产出的账不会互相顶替。

## 什么时候会"看起来没发生转化"

按这个顺序排查：

1. **规则没被选中**：条件不满足时掉落物根本不会消失，规则会按退避节奏反复重试（1 秒 → 2 秒 → 4 秒 …… 到上限为止），它只是"还没到时候"或"地方不对"。见 [条件配置](03-conditions.md)。
2. **规则没加载或没被启用**：`enabled: false`、id 撞名被更高来源的同名规则覆盖、JSON 字段写错导致该条被拒载。改动规则后需要重载才生效。见 [首次使用与生效流程](01-getting-started.md) 与 [来源层与覆盖](06-layers-and-overrides.md)。
3. **源物品不足一组**：整堆数量小于每组固定成本（成本写 2 却只剩 1 个）时一组都开不出来。你会看到掉落物到时间后消失、又在原地附近重新出现一份一模一样的掉落物——这就是返还，而且这份返还物不会再被转化。
4. **候选容量不足**：触发点周围同类产物（物品、生物、经验）已经达到服务器配置的上限时，能开组的候选会被跳过；所有候选都开不出组时整堆原样返还。见 [服务端配置](07-server-config.md)。
5. **这个结果自己被跳过**：效果级 `conditions` 不满足、或 `chance` 没命中。此时源物品照常被扣，只是看不到产出。见 [效果](04-effects.md)。
6. **产出被延迟**：效果写了 `delay_ticks` 时，产出会晚于掉落物消失的那一刻出现（例如延迟的闪电、分批生成的生物）。
7. **产出落在别的位置**：`fill_origin: false` 的方块不会填在触发位置本身；开了 `safe_spawn` 的生物可能出现在旁边的格子上。

一句话的排查顺序：先确认规则本身被选中（启用、加载、条件），再看成本与数量（够不够一组、催化剂够不够），然后看容纳上限，最后才看效果自己的条件、概率与延迟。
