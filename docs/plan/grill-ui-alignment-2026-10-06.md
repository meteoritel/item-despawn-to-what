## Bug 与联动待确认项

### B01：省略 enabled 时，UI 把有效默认 true 显示为未勾选

- 页面/入口：新建空白规则 → 基本信息；也影响已有 JSON 省略 `enabled` 的规则。
- 证据：`BuiltinEditorDefaults.java:23` 调用空白工厂并省略 enabled；`FormView.java:151` 直接装载原始字段；`FormControl.java:678` 的 BoolControl 将缺失值显示为 false；`core/model/RuleCodecs.java:143` 的权威默认值为 true。截图 `23.03.05` 与 UI 未勾选表现一致。
- 复现步骤（待游戏执行）：新建规则，不操作启用开关，查看其勾选状态；补全规则并应用后核对有效启用状态；另检查已有省略字段的规则。
- 预期：控件表达有效 true，或明确表达“未指定，默认启用”；仅查看不写入 enabled。
- 实际：当前装载代码必然把缺失值显示为未勾选；`store()` 在未编辑时仍保留缺失字段，因此 UI 与权威语义不一致，不能宣称后端已将规则停用。
- 影响：布尔控件对缺省 true 字段的显示正确性；至少确认规则 enabled，其他布尔字段逐项核对默认契约。
- 频率：给定缺失字段时为确定的静态代码路径；游戏内发生比例与截图版本一致性未验证。
- 建议：P1，客户端回填/描述符责任；无需先改服务端默认值。

### B02：纯文本弹窗的测量与实际绘制不一致

- 页面/入口：存在未应用改动时关闭编辑界面，出现“放弃改动”弹窗。
- 证据：截图 `23.04.00` 的正文压到内框下沿；`UiModal.java:221` 高度只算行高，并按 `preferredWidth - 2*PADDING` 换行；`:327` 绘制按内容宽度再次减 `2*PADDING`，且从内容顶端加 PADDING 开始绘制。`UiTheme.java:27` 的 PADDING 为 4。
- 复现步骤（待游戏执行）：新建未应用草稿，关闭界面观察弹窗；在较窄窗口与较长消息下检查换行后是否仍完整显示。
- 预期：测量与绘制使用相同文字可用宽度，高度容纳文字和上下内边距。
- 实际：源码确认宽度与内边距计算不一致；截图可见正文与边框拥挤。未执行新的动态复现。
- 影响：使用默认纯文本消息的 UiModal；自定义内容弹窗需独立检查，不能直接纳入相同影响范围。
- 频率：提供的相关截图 1/1 可见；跨缩放、长消息与其他弹窗的发生率未知。
- 建议：P1，通用 UI/widget 测量责任，与服务端无关。

### C01：目录按中文显示名搜索可能无结果

- 页面/入口：输入页“从目录选择”及其他共用目录面板；截图未打开该页面，因此属于关联调查项。

- 影响/频率：走同一路径的目录存在风险；未做游戏复现，频率未知。

## 设计前置讨论：规则树与实体产出抽象

以下保留前一轮推荐与对比的历史记录。最新结论：D01 被用户接受；D02 的“仅统一分类”推荐被用户否决，改为后端也统一、按子类分发。已更新词汇表并记录 ADR-0026，字段与行为细则待确认；未改动旧冻结规格。

### D01：采用按玩法用途分类的虚拟规则树

推荐：规则管理默认采用可折叠的虚拟分类树；分类从当前规则内容推导，以规则 ID 维持身份。实体父层是否在主导航中显示，依赖 D02 与下一轮可读性选择。

现状证据：`RuleEditorScreen.java:116` 使用 UiListView；现有 UiTreeView 已支持根节点、折叠、选择与激活，见 `client/ui/widget/UiTreeView.java:98`、`:133`、`:139`。替换视图可复用已有组件，但选中与折叠状态仍须由业务层按稳定 ID 恢复，不能假定换树后自动保留。

实际文件关系：`core/load/RuleSourceIndex.java:13` 按规则 ID 合并数据包基础值、覆盖值与控制条目；`core/network/protocol/RuleSnapshotEntry.java:17` 只下发 id、来源、状态、基础/覆盖/生效内容等，不包含完整文件目录。真实磁盘树若作为管理主视图，需另行提供来源路径与文件操作契约。

| 方案 | 美观性 | 可读性 | 可扩展性与成本 | 分组及编辑影响 |
|---|---|---|---|---|
| 保持平铺列表 | 最简洁、无缩进；条目较多时重复两行信息难扫描 | 少量规则或搜索定位快；产出差异与整体结构不明显 | 新类型可直接增加规则；规模增长主要依赖筛选 | 沿用选择/双击编辑；不提供类别上下文 |
| 按实际文件目录做文件树 | 路径层级清楚，但深路径和命名空间挤占窄屏宽度 | 熟悉数据包的人能定位文件；普通使用者需理解来源、覆盖、同 ID 合并 | 与存储布局耦合；当前快照缺完整路径；拖动/重命名可能触及规则身份与覆盖关系 | 目录不是玩法分类；移动叶子容易被理解为移动文件；需要新增服务端契约，不能作为本轮纯 UI 改动 |
| 按玩法用途统一为虚拟分类树（推荐） | 图标、计数、缩进建立层级；限制深度、隐藏空组，避免层级负担 | 类别 + 可读规则名便于浏览；保留全局搜索与展开命中路径 | 新效果增加分类映射即可；未知类型有回退；不依赖文件路径 | 分组节点只展开；规则节点预览/编辑；不对应文件移动，不改变规则优先级 |

具体规则建议：

- 扫描全部候选中的效果，按用户操作语义识别产出类别；不用某个最终生成的 Java 类反推全部分类。
- 消耗效果不决定产出分类；已知单一类别归对应组，同类多个效果也留在该组；跨类别归“组合规则”。“多个候选”本身不等于组合类别。
- 每条规则只出现一次；来源、停用、屏蔽、未应用改动作为状态与筛选。
- 未完成草稿、内容非法、仅消耗、未知扩展要有明确回退；存在未知效果时不能假定只会产出已知类别。
- 单击规则预览，双击或 Enter 编辑；分类节点只展开，不打开表单。搜索自动展开命中路径，清除搜索恢复原折叠。
- 草稿改产出后允许归组变化，但当前编辑对象始终按 ID 保持；不突然关闭表单或将下一行当成当前规则。
- 分组重算应在快照/草稿变化时进行，避免每帧扫描；可折叠本身不等于已经实现列表虚拟化。

取舍结论：树的价值是可浏览的语义结构，不是单纯更好看。少量规则时增加类别行和展开动作确有成本；限制到少量可理解层级、配合搜索和自动展开，比引入真实文件目录更适合当前约束。

### D02：统一实体产出的概念与分类，保留类型专用参数及现有效果契约

推荐：将直接生成掉落物、生物/其他实体、经验的操作归入“实体产出”这一概念层；明确子类别，并在编辑中使用对应专用表单。现阶段不把 spawn_item / spawn_entity / spawn_xp 的 JSON type、Codec 与执行器合并成一个通用 spawn_entity。

“都是 Entity”是运行时共同点，但“仅实体类型不同”不足以描述当前契约：

| 操作 | 当前类型与主要参数 | 数量单位与特殊行为 |
|---|---|---|
| 掉落物产出 | spawn_item；item/id 或标签、count、limit/radius | count 为物品件数；按堆叠大小拆成 ItemEntity；邻近限制统计物品件数，非实体个数 |
| 生物及其他实体生成 | spawn_entity；entity/id 或标签、count、age、limit/radius | count 为实体个数；age 只在可年龄化生物上生效；候选 safe_spawn 控制安全位置搜索 |
| 经验产出 | spawn_xp；amount、per_source_item | amount 为经验点数；可按实际消耗源物品数缩放；ExperienceOrb.award 负责发放，不能把 amount 当球个数 |

证据：`core/type/effect/exec/SpawnItemExecutor.java:71`、`:101`；`SpawnEntityExecutor.java:71`、`:217`；`SpawnXpExecutor.java:28`、`:38`。`core/model/Effect.java:11` 已提供所有效果的公共抽象与延迟/概率/条件契约。

| 方案 | 收益 | 成本与限制 | 分组及 UI 编辑影响 |
|---|---|---|---|
| 保持当前独立分类和表单 | 路径短、操作具体、兼容现有数据 | 共性分散；“生物”不足以涵盖 spawn_entity 的实际范围；新增类型需统一维护分类 | 物品、生物、经验作为平级入口；可继续专用表单，但入口组织需要规范 |
| 统一概念/分类，保留专用效果（推荐） | 共享产出分类规则、入口与通用效果字段；保留参数的准确语义 | 分类信息需有统一来源与未知类型回退；前端扩展分类不能假定后端已拥有这份元数据 | 可用“实体产出 → 掉落物 / 生物 / 其他实体 / 经验”；主要导航也可提升常用子类；选择子类后进入专用表单 |
| 连同后端模型/JSON 统一为带子类的实体生成效果 | 未来若有大量共享生命周期能力，可集中抽象 | 必须保留有区分的参数结构与计量单位；迁移旧 JSON/type/描述符、容量预算与扩展 SPI；没有当前收益足以覆盖成本的证据 | UI 仍要按子类型分支，不能只显示“实体 ID + 数量”；需单独架构任务与迁移方案 |

编辑交互建议：

- “添加效果”先呈现用户可理解的操作；实体产出分类下有掉落物、生物、其他实体和经验。常用入口可以直接露出子类，减少额外点击。
- 掉落物选 ITEM 目录并编辑件数；生物/其他实体选 ENTITY 目录并按能力展示参数；经验编辑点数与计算方式，不要求用户选经验球 EntityType。
- 延迟、概率、条件继续复用已有通用效果能力；位置、安全、邻近上限等仅在实际支持的类型上出现。
- 同一候选可以同时包含“2 件物品 + 5 点经验”等多个效果。实体概念层不能把它们强制压缩成一个互斥子类。
- 切换效果子类应走明确操作，并说明不兼容参数如何处理；仅浏览类别不得转换效果 type 或丢弃数据。具体保留/转换规则待下一轮。
- 第三方类型无分类信息时回退为“扩展/未知”，无编辑器时继续原样只读，不按猜测改字段。

分类边界反例：箭雨的箭也是实体，但 ArrowRainExecutor 的操作是分波箭雨，属于世界事件；闪电执行也使用实体实现。主类别应表达“这个效果在做什么”，不能仅以是否创建 Entity 决定。可有多个技术标签，但每条规则的主归组须稳定。

领域关系建议：规则包含候选结果，候选结果包含效果，部分效果生成实体产物。候选结果本身不是实体；天气、爆炸、方块放置和消耗仍是其他效果。

### 服务端共享上限与满额策略：当前决策前沿

- 配置现状：统一服务端配置入口是 `config/itemdespawntowhat/server.json`，由 common ServerConfig 与两平台 RuleRuntimeHost 接入；不是历史旁路 server.toml。本轮不改配置代码。

- 数值建议可由实现方案给出并让管理员在服务端调整；未经性能测试不把某个默认数量或半径宣称为性能安全保证。

### Q13：已开始组执行途中受阻（已确定）

边界例子：开组前附近 50 个经验球、上限 64，确认有空间后支付成本，但在延迟或分批执行期间其他产出填满附近空间。

- 用户未选先前的有限等待或立即终止方案，而是明确“已经开始执行后就不管上限了，允许执行结束后短暂超过上限”。
- 最终行为：各邻近限制都是开组准入阈值；组开始后完成正常执行，不再因邻近阈值截断、等待或取消。新组继续遵循容量预检；受阻未开始组不支付成本，剩余源物品保留/返还。
- 必须取消产物执行器每批按邻近上限截断已开始组的旧分支；已有调度预算、区块可用性检查和效果概率/条件仍按相应契约处理。
- 不新增因阈值满额而等待的超时字段或持久经验队列；不清理已经生成的超额产物。
- 已知限制：这不是硬实体上限，多个已开始组与其他产出可能使存量超过阈值；回落时长由拾取、消失等世界变化决定，不能保证固定时长。“短暂”暂按允许已开始组收尾理解，不设主动定时删除。
- 未修改执行代码。主要模型与分类方向已收敛，进入具体 UI 交互与验收讨论。

### B06：无图标目录条目的文字占位不可见

- 入口：实体目录及其他没有物品图标的目录条目。
- 源码：`RuleEditorP4Panels.java:142–162` 只为 ITEM/BLOCK 解析 ItemStack，其他类型无图标；`UiCatalogGrid.java:363–369` 对无图标名称的裁剪宽度传入 1 GUI 像素，通常无法容纳一个字符。
- 实际静态行为：实体目录没有实体图标，文字回退可能空白；不是服务端未返回实体类型，未作游戏内复现。
- 预期：始终有可辨认类别占位、名称与完整 tooltip，新增实体图标方式另行确认。
- 待执行步骤：打开实体目录，对照原版生物、无刷怪蛋实体与模组条目，核对图标/名称/选择反馈；优化后执行。
- 影响：对象识别与目录可用性；频率未实测。
- 建议：P1 可用性，客户端目录解析与 UI widget 责任；新增图标缓存与回退纳入 UI 任务。

### C01 补充：完整本地化名称搜索的可行边界

- 请求 `RequestRuleCatalogPayload.java:13–17` 支持 filter/page/pageSize，每页最多 200；`RuleCatalog.java:16–22` 回包有 type/revision/entries/lastPage，没有总数或实际页号。
- `RuleEditorP4Panels.java:226–229` 将过滤词原样发服务端；服务端 `RuleCatalogService.java:120–140` 匹配原始 ID、label 和 subLabel，物品等 label 在 `RuleCatalogSources.java:85/95/105` 为翻译 key，收到后客户端才翻译。
- `RuleEditClientWorkspace.java:180/371–379` 同类型只收最新 requestId，覆盖单页缓存；完整缓存应串行分页并统一请求调度，不把当前页筛选误称全目录搜索。
- 可只改客户端：按需拉取当前目录全部页，依据玩家当前语言建立名称/ID 索引，加载未完成时明确结果不完整；无需让服务端翻译中文。此方案随后已获 Q20 确认，尚未实施。
- 已知限制：10,000 条至少 50 页，首次加载时延未实测；服务端每页计算源 revision，客户端完整索引占 O(N) 内存。现有 revision 仅 ID 集合哈希，不能保证元数据变化的完整检测，未发现主动失效推送。不得擅自重做此协议或宣称立即响应全部数据变化。
- Q19/Q20 的方案对比与事实证据见实施草案，用户结论记录如下；旧推荐不代表最终实施范围。

### Q19/Q20 用户结论

- Q19：用户要求“一步到位”，实体使用框内 3D 模型渲染，绕竖直中轴旋转，自适应缩放以适合框大小。取代前一轮刷怪蛋代表图标/仅选中项 3D 的建议；可见实体图标直接使用 3D，需客户端生命周期、缩放和渲染状态恢复设施。
- Q20：接受按需缓存完整目录、客户端按当前语言名称和 ID 搜索；加载中显示“正在加载”和几个点转圈的动画，视觉动感借鉴 Windows 启动。原接口不变，仍保留首次分页加载时延与 revision 限制。
- 继续只读 Level 2 核对通用实体渲染、碰撞尺寸与可视模型范围差异，不提前宣称所有模型均能精确测量。加载动画、错误/重试/未完成状态纳入 UI 任务，不把转圈当作已完成或进度百分比。

### Q19 的 Level 2 核查结论与 Q21 确认

- IDEA 的 vanilla merged jar 证据：EntityRenderDispatcher 支持通用 Entity，InventoryScreen 的 GUI helper 只支持 LivingEntity；EntityType.create(Level) 可返回 null。无须新 Mixin 实现基本 3D 路径。
- getBbWidth/getBbHeight、默认 getBoundingBoxForCulling 对应碰撞尺寸，不是实际模型可视边界。旋转时龙翼、尾部和自定义模型可能超出该尺寸，不能宣称一条基于碰撞框的公式适配所有模组模型。
- 原版 helper 修改 shadow/camera 状态后不完全恢复原值；具体实现需直接 renderer 路径或显式状态管理，并 finally 恢复，以免后续图标受污染。
- 无模型、无 renderer、创建失败或 renderer 异常是预览的独立状态，不能只画空槽或编造实际产物。Q21 用户已接受分层尺寸修正和模组实测，并指定屏障方块的物品图标+“预览不可用”统一兜底；不在世界放置屏障，也不因预览失败禁止选择。
- 加载动画可通过现有 GUI 绘制和单调时间实现，不需要美术贴图或服务端修改。未修改 Java/JSON，未执行构建或游戏测试。
