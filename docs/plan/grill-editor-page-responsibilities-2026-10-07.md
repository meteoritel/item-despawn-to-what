## 1. 四页职责（Q1 已确认）

| 页面 | 回答的问题与职责 | 使用场景与操作流程 | 边界 |
| --- | --- | --- | --- |
| 基本 | 这条规则叫什么、是否启用、与其他规则竞争时谁优先 | 识别或管理规则：查看当前名称 → 按需设置显示名或恢复自动命名 → 设置启用状态 → 按需编辑优先级和备注 | 名称与备注不改变输入、触发、产出或规则身份；优先级影响命中规则选择 |
| 输入 | 哪些源物品参与、催化剂和流体是什么类型、每轮如何消耗 | 选择源物品或标签 → 按需排除 → 确认源消耗 → 勾选添加催化剂/流体并选择类型 → 按需配置每轮消耗数量 | 定义对象类型与消耗量；触发门槛未填时以对应消耗量为默认值，明确门槛独立；未添加时不占用配置框 |
| 触发 | 这些掉落物什么时候、满足哪些条件才转化 | 选择触发途径 → 自然等待 → 自动带入输入已定义的催化剂/流体 → 配置存在要求与其他环境条件 → 需要时组合全部、任一或取反 | 真正定义触发条件在此；输入定义的类型与存在数量/源流体要求分工，保留原条件作用域 |
| 结果 | 转化后执行什么、生成什么、多个方案如何选择 | 定义行为：查看或添加方案 → 添加动作并填产出参数 → 按需增加同方案动作 → 多方案时选择轮流或按顺序选择 → 按需配置单动作高级项 | 每组只选择一个方案；同方案内可以执行多个动作；单动作概率、延迟、条件属于结果页 |

协作流程：源匹配确定候选规则，启用状态与规则优先级参与筛选；触发途径和规则条件决定能否转化；输入成本与结果可执行性共同影响整组准入和结算；选中方案中的动作执行。页面顺序是编辑分工，不等于要求玩家按固定向导顺序操作，也不表示运行时先无条件扣款再检查结果。

示例（用于检验职责，不是新增默认规则）：将腐肉变为泥土。输入页选腐肉并设每组 1 件；触发页选自然、等待 300 秒、无附加条件；结果页设一个方案，添加生成泥土掉落物的动作；基本页按需命名“腐肉变泥土”。不改显示名也应能识别和使用此规则。

## 3. 基本页字段事实（职责确认后的修正分支）

用户提到的“备注名”在当前 UI 与模型中是“备注”，不参与命名。既有领域词汇表已区分规则展示名、自动展示标题、备注和规则 ID，本轮不另建重复词汇表。

| 项目 | 显示名 | 备注 |
| --- | --- | --- |
| 绑定 | 草稿根字段 `display_name` | 草稿根字段 `notes` |
| 数据来源 | 服务端规则快照建立客户端草稿；已有规则来自有效规则/覆盖/基底快照 | 同左，保留完整原文 |
| 空白新建默认值 | 字段缺失，输入为空；标题使用自动生成值，但不把它写成显示名 | 字段缺失，输入为空 |
| 模板/复制 | 保留模板或原规则的完整显示名，另生成身份 | 保留模板或原规则的完整备注 |
| 规范化与校验 | 已编辑文本 trim；空视未设置；后端与客户端规则校验上限 128 Unicode 码点 | 编辑时保留空白，真正空串删除字段；UI 规格上限 1024 码点，未发现后端备注专用长度限制 |
| 当前控件限制差异 | 实际 `EditBox` 上限是 128 UTF-16 单元，遇到补充平面字符比码点规则更严 | 实际上限 1024 UTF-16 单元；已有超长文本完整回填，不在浏览时截短 |
| 正确展示方向 | 首次回填从开头可读；空值以占位说明自动命名；人工名称不改变 ID | 首次回填从开头可读，长文本能完整查看/编辑；不充当标题 |

本例内置文件 `common/src/main/resources/data/itemdespawntowhat/idtw/rules/builtin_multi_effect.json:4` 的名称是完整的“钻石雷鸣 / Diamond Thunder”；`:5` 的备注是完整段落，结尾为“叶级 negated 已删除。”。截图的“er”“除。”分别是它们的尾部文本。调查时 `neoforge/run/config` 未发现此规则的覆盖文件。

已确认根因链：

1. `UiTextInput.java:47` 先以宽度 24 构造原版 `EditBox`。
2. `RuleEditorEditPages.java:371` 在布局前 `reload`；`FormControl.java:564` 完整回填 `loadedText`。
3. 原版 `EditBox.setValue` 将光标移到末尾并按当时窄宽度计算水平滚动位置；IDEA vanilla 反编译 `EditBox` 的 `setValue`、`scrollTo` 与 `renderWidget` 已核对。
4. `UiTextInput.java:131` 后续只更新宽高，未复位滚动位置；绘制继续从 `value.substring(displayPos)` 开始，因此只看到尾巴。

这不是字段绑定错位或原始字符串被截短。首次打开、重建控件或切回基本页再次先回填后布局时会再次出现。`FormControl.java:580` 在未修改时保留完整原值，不会把眼前的两三个字作为完整值写回。

最小修复方向：为程序回填明确从开头展示的约定；不在每帧布局或用户输入期间强制移动编辑光标，不迁移或改写 JSON。另单独处理自动标题语义、Unicode 长度限制与备注阅读能力。

## 4. 可用性验收目标

以下目标来自用户“无需额外说明即可看懂并正确使用”的要求，不作为另一个需要重复批准的目标。具体界面方案随职责裁决收敛。

- 每页首屏能看懂自己要完成什么、当前有效值是什么、下一步入口在哪里；优先靠分组、具体字段和明确按钮表达，不给每页堆说明段落；tooltip 只补充细节。
- 空白规则能从输入、触发、结果完成最小规则，基本页无需填名称也可应用；已有规则无需进入技术详情即可确认输入、时机、每组消耗和产出。
- 单方案不要求理解“隐式结果”；多方案清楚说明每组只选一个，同方案动作不是互斥选项。
- 未满足必填项或全部触发未选才显示对应错误，并能定位；普通说明不伪装错误。
- 仅打开、切页或浏览不生成脏改动、不截短全文、不改变身份；真正编辑支持撤销与重做。
- 小窗口能读到单位和关键说明、滚动到必要字段；无需靠额外文档解释才能完成基础操作。

## 6. 第一轮答复后的补充

用户已明确要求：基本页适当增加文本框和滑条高度；删除最后一行文本；规则注册名放到最上面；修复恢复自动命名按钮点击后不失焦、看不出效果的问题。

截图底部“钻石雷鸣 / Diamond Thunder：非 Y 高度… → …”是编辑器固定摘要（`RuleEditorScreen.java:486`、`:559`），不是备注或名称的一部分。基本页末尾另有只读 ID 和结构版本，排版在 `RuleEditorEditPages.java:1204`。下一轮明确删除的是固定摘要及其跨页范围；最上方 ID 使用稳定规则 ID，不把玩家显示名替换为 ID。

恢复自动命名当前调用删除 `display_name` 的草稿操作（`RuleEditorEditPages.java:395`），这是既有正确业务语义。特别是人工名称恰好等于自动标题时，标题可能不变，仍需以输入框清空、按钮状态和简短反馈确认动作完成。

### 恢复自动命名：已证实的故障

- `RuleEditorEditPages.java:388` 先登记文本表单，再登记恢复按钮；`:1918` 鼠标释放遇首个消费组件就停止转发。
- `UiButton.java:149` 按下仅设置 pressed，`:161` 释放才激活按钮；`FormView.java:674` 转发到输入框，`UiTextInput.java:167` 无条件委托原版释放处理。
- IDEA vanilla `AbstractWidget` 反编译证实左键释放会返回 true，不要求此前按下过该控件。因此表单吞掉释放，恢复按钮回调未执行，并可能保留 pressed 外观。这是确定的事件路由问题，不只是提示不明显。
- 鼠标按下前宿主已有 `focusClicked → focusOn`，理论上会清除输入框焦点；尚不能从代码证明用户所述失焦问题是输入框真的持有焦点，可能是按钮保持 pressed。验收分别检查输入光标、继续输入的归属及按钮外观。
- 回调若成功触发，会提交当前缓冲、删除显示名、重建表单并清理旧焦点；没有发现旧值再次写回的路径。
- `RuleEditorEditPages.java:387` 按是否有显示名设置按钮状态，但 `:1746` 的统一启用覆盖了这个状态。应保留控件自己的可操作条件。
- 修复公共释放归属/转发约定，不为恢复按钮写特例；恢复后显示名为空、当前标题自动刷新、按钮禁用，并给一条简短成功反馈。支持一次撤销恢复原名称。

### 成本边界：补充事实

- 客户端与服务端均禁止 `source_cost` 与 `consume_source` 同时声明，也禁止 `catalyst_cost` 与 `consume_catalyst` 同时声明（`RuleEditorScreen.java:1406`、`RuleValidation.java:67`）。不应把非法草稿解释为合法的覆盖优先级。
- 每种消耗动作在整条规则、跨所有方案仅允许一条（`RuleValidation.java:179`、`:201`）；`RuleCostBinding` 查找第一条对合法规则成立。
- `consume_source.count` 决定所有开始组的源成本，并非只对其所在方案生效；源支付不因该动作的概率/条件跳过而返还（`BuiltinTypeRegistries.java:43`、`ConversionSettlement.java:490`、`:624`）。
- `consume_catalyst` 是所属方案内的动作；固定 `catalyst_cost` 才是整条规则的开组支付要求，两者不能都标成无区别的全局成本。
- 已有计划要求源/催化消耗主要在输入页编辑，保留原动作路径，不重复生成固定成本（`plan-gui-rule-update.md:100`）。本轮建议保持这项契约，只明确主入口与跳转。

## 7. 第二轮问题

- Q3（已确认）：基本页从上到下为只读规则 ID、显示名与恢复按钮、启用与加高的优先级控件、默认 2–3 行的备注输入。删除基本页固定底部摘要、重复 ID 和无意义的结构版本行，不添加长说明。显示名留空以“自动命名”作占位，顶部当前名称显示实际生效标题；回填从开头阅读。仅基本页删摘要，其余页后续按各自职责整理。
- Q4（范围已明确）：输入页编辑源物品、催化剂物品、流体浸润情况，以及是否存在、消耗设置、物品与数量。用户特别指出催化剂和流体可以被消耗，区别于其他被动环境条件。这替代之前只讨论源/催化剂成本入口的范围；是否改变执行语义尚未裁决。

用户要求的增高、上移 ID、按钮故障修复和 Q3 布局已记录为明确范围。新增输入要求整合方案收敛后汇总可执行方案，按用户整体理解确认进入实施。

## 8. 输入要求整合：事实与第三轮问题

界面统一称“输入要求”，其中“存在要求”和“消耗设置”分开表达。代码领域仍遵循条件纯检查、成本或动作承担消耗的契约（`ConditionEvaluator.java:5`），页面归属不能隐含改变执行语义。

| 当前能力 | 位置/数量 | 实际行为 |
| --- | --- | --- |
| 催化剂存在检查 | 源物品所在 1×1×1 方块格；至少 1–64 件 | 只检查，不扣物品；不足条件不成立 |
| 固定催化剂成本 | 半径盒，默认半径 1，数量 1–64 | 开组前足额支付；不足不开组 |
| 催化剂消耗动作 | 半径盒，数量 1–64，属于具体方案 | 按实际可用量扣除；不足可能跳过，不会自动取消其他产出 |
| 流体存在检查 | 掉落物所在一个方块；类型与是否源方块，无数量 | 只检查，不修改世界 |
| 流体消耗动作 | 对应位置一个方块，无数量或扫描半径 | 真正移除流体；无流体则跳过；不按流体量计算组数或预留份数 |

证据：`CatalystPresentEvaluator.java:34`、`FluidPresentEvaluator.java:24`、`CatalystCost.java:25`、`ConversionSettlement.java:235`/`:464`、`ConsumeCatalystExecutor.java:57`、`ConsumeFluidExecutor.java:62`/`:71`。流体在含水方块上关闭含水状态，其余匹配流体所在方块被移除。这里的“要求源方块”指流体源方块，不是源掉落物。

已有注释中的“流体只作为实时存在条件”只描述组数/份数预留，不代表 `consume_fluid` 没有移除副作用。已同步澄清词汇表；代码注释错误暂记待修：`ConsumeFluidEffect.java:24`/`:42` 误解释 require_source，`FluidPresentCondition.java:20` 误提相邻位置。存在检查与消耗的直接流体 ID 匹配还有差异：前者非源模式支持同族流动变体，后者精确匹配（`FluidPresentEvaluator.java:46`、`ConsumeFluidExecutor.java:92`），不能无条件互换。

另一项边界：现有催化剂/流体检查可以在任一、取反或单动作条件中。例如“有催化剂 **或** 下雨”不同于“必须有催化剂 **且** 下雨”。把其参数移到输入页时，不能直接抽成全局必需输入而丢掉原逻辑。

- Q5（已确认）：保留既有运行特性；用户明确流体按存在判定、不换算消耗份数是有意设计。保留其类型与流体源判断、独立移除动作；不改为按流体数量支付、不新增流体数量字段，也不改成无流体仍可通过。
- Q6（已确认并细化）：新增简单存在要求默认整条规则必须满足，已有任一/取反/单动作作用域保留。用户进一步明确：输入只定义这两类条件的催化剂物品类型和流体类型；勾选添加后才展开后续选择框；触发页自动带入对应条件，真正配置存在判定和组合关系。先前“全部催化剂/流体条件参数在输入”的建议由此替代。

Q5 与 Q6 分别决定是否改变运行语义以及检查的逻辑作用域，不能用同一个“是否存在/消耗”开关默默推断全部答案。

## 9. 输入定义与触发条件的关联

实现约束：现有 `conditions` 中的具体条件叶是单一事实源。输入编辑 `catalyst_present.items` / `fluid_present.fluid`；触发读取同一叶配置存在数量、流体源要求和组合，不新增顶层类型定义字段、不用复制两份对象类型实现“自动填写”。页间同步不得让旧表单缓冲覆盖新类型。

勾选新增时空树直接新增叶，已有根不是全部组合则将完整旧根与新叶放入全部组合；不根据触发页当前选中的任一节点擅自插入。已有条件叶可能有多个同类，也可能位于任一/取反内部；按确切路径逐项绑定，不能查找到第一个就覆盖，不能按类型全删。已有动作局部条件不提升为整条规则条件（`RuleValidation.java:119`/`:141`，`UiConditionTreeEditor.java:345`/`:730`，`BuiltinEditorDefaults.java:66`）。

新催化剂条件保留 items 为空、待选物品的中间态，但不预写 count=1，改为未填写门槛以继承消耗量。新流体叶工厂当前将 require_source 写为 false（`BuiltinEditorDefaults.java:154`），而 JSON 省略时后端默认 true；流体现有特性保留，不顺手统一这两种形态。

- Q7（被 Q9 修正）：此前共享一个逻辑数量的方案已撤销。以第 10 节的独立数量、默认门槛方案为准。
- Q8（已确认）：取消勾选添加，删除对应的存在条件和类型定义；触发页删除对应条件时输入同步取消。消耗另有独立开关，取消存在检查不顺带删除消耗动作或固定成本；删除仅作用当前关联项、整理空父组且可一次撤销。

已存在多同类条件时逐项呈现简短编号和必要作用域，不用一个总开关删除整类；显示策略可按数量折叠列表，不改变绑定关系。关联删除确定后收敛实施，不再追加与本任务无关的设计分支。

## 10. 每轮消耗与默认触发门槛（Q9 最终裁决）

用户明确：开发阶段无需考虑数据迁移；两个数量独立更灵活。输入页填写每轮消耗量 C，触发页可选填写门槛 T。T 未填时有效门槛=C；T 已填则使用 T。修改 C 只更新自动门槛的展示与有效值，不覆盖明确 T；清空 T 恢复跟随。门槛不会反向改消耗量。

示例：输入消耗 2 件、触发门槛留空，则至少 2 件；输入改为 4 件，门槛继续留空且有效值变为 4。若玩家明确填写门槛 6，则输入消耗量之后的修改都保留门槛 6。

UI 仅显示“每轮消耗”和“最低数量”，默认门槛短提示为“默认：N”，有值则显示玩家值，不增加同步说明段落。类型的关联与 Q8 删除同步继续生效。

### 当前实现约束

`CatalystPresentCondition.java:25` 的 count 是 int，codec 在 `:42` 将省略直接转成 1；求值器直接读取 count。`ConditionContext` 没有所属规则或催化剂消耗配置，`ConversionRuntime.java:536` 还在候选循环外创建共用上下文。因此不能只改 UI：存具体数字会丢掉“未填写”的持续继承状态，直接省略又会被现后端固定解释成 1。

需要让条件模型/codec保留 count 未填写状态，明确值仍校验 1–64，未填值按对应催化剂输入派生。不得通过“门槛恰好等于旧消耗量”猜测自动模式。

### 后端方案比较

| 方案 | 实现职责 | 取舍 |
| --- | --- | --- |
| A：求值上下文解析默认值 | 条件 count 可选；上下文携带所属规则的成本解析器；每条规则与局部动作使用正确作用域 | 派生时机直接，但扩展公开 ConditionContext 和求值链契约 |
| B：声明与运行投影分离（已采用） | 保存/编辑保留可选 count；运行入口按所属规则解析有效门槛，生成运行条件投影 | 保留现有上下文职责，需要共用投影入口，覆盖普通规则和绕过索引的 debug 规则 |

两种方案都不新增迁移流程；默认跟随必须是后端可执行语义。运行派生结果不反写到声明 JSON；只在规则/消耗配置变化时刷新对应投影，避免每次条件检查重复构造整棵树。具体缓存接点以现有生命周期核对，不另建第二套规则索引。

类型关联按确切条件叶、对象引用与成本/动作确定；任一、取反和局部条件不升级成全局条件，不按类型名称盲绑。没有匹配消耗配置时的默认存在门槛为 1 件（Q10 已确认）。默认门槛声明与运行投影的架构分工见 [ADR-0027](../adr/0027-catalyst-threshold-runtime-projection.md)。
