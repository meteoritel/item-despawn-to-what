# v1.2.1 旧生成器迁移评估（P8）

状态：已定稿（2026-10-03）  责任人：tree-dev  基线：git tag `v1.2.1` = `5a85911b68fc84e809d13099ab32a711d6437076`
依据：`docs/plan/plan-frontend-rewrite.md` §13（:635-672）、§13.2 决策表（:665-668）、§14（:688）；本文件所有旧行为结论均来自 `git show v1.2.1:<path>` 的源码，行号按该 tag 计。

## 1. 结论

**采用 §13.2 方案 B：破坏性更新（不提供旧配置的自动迁移 / 转换器，退役 /idtw config convert）。**

一句话理由：旧五类配置与最终规则模型之间的差异不只是字段改名，而是**执行模型差异**——轮数上限算法（旧含催化剂存量与结果容量共同压缩，新只按源物品）、世界现象的时间展开参数与其可配置间隔、方块放置形状枚举（4 值含 3D，新只有 3 值平面）、爆炸方向与闪电纯视觉、经验球的三元倍率换算；其中若干项在最终模型里**没有承载字段**（结构性缺失），不是转换难度问题。强行写转换器只能「拒绝这些规则」或「静默降级」，与 §13.2「不悄悄丢字段、有歧义就停止并报告」冲突。

同时保留两条底线：不自动删除或改写用户磁盘上的旧 JSON；提供一份旧→新对照与「无法保留」清单的更新说明。

## 2. 基线与评估方法

- 基线是 tag `v1.2.1`；该 tag 的仓库内**不存在生成器输出样例**（`git ls-tree -r --name-only v1.2.1` 只有 `lang/en_us.json`、`lang/zh_cn.json`、`fabric.mod.json`、`itemdespawntowhat.mixins.json` 等 4 个 json），因此本评估只能依据生成器源码语义，不能引用实物输出文件。
- 旧链路只读路径（`common/src/main/java/com/meteorite/itemdespawntowhat/` 下）：`config/ConfigType.java`、`config/handler/BaseConfigHandler.java`、`config/conversion/BaseConversionConfig.java`、六个 `config/conversion/*Config.java` 子类、`config/catalogue/{CatalystItems,InnerFluid,PotionEffect,SurroundingBlocks}.java`、`config/WorldEffectType.java`、`condition/{ConditionCheckerUtil,ConditionContext}.java` 与 `condition/checker/*`、`server/task/{PlaceBlockTask,ExplosionTask,LightningTask,ArrowRainTask}.java`。
- 最终模型侧对照文件：`core/type/effect/*.java`、`core/type/effect/exec/*.java`、`core/type/condition/*.java`、`core/runtime/ConversionRuntime.java`、`core/command/RuleConvertService.java`。

## 3. 旧模型关键语义（逐条带证据）

### 3.1 文件与字段
- 五类顶层文件（每类是一个 JSON 数组）：`item_to_item`、`item_to_mob`、`item_to_block`、`item_to_xp_orb`、`item_to_world_effect`（`config/ConfigType.java` 的五个常量，各带文件名）。世界现象不单独成文件，由 `side_effect` 字段在 `item_to_world_effect.json` 内区分 5 种。
- 通用字段（`BaseConversionConfig.java:53-89`）：`item`(:53)、`result`(:57)、`source_multiple`(:61)、`result_multiple`(:65)、`conversion_time`(:69)、`need_outdoor`(:73)、`dimension`(:77)、`surrounding_blocks`(:81)、`catalyst_items`(:85)、`inner_fluid`(:89)。
- 子类字段：`result_limit`（`BaseItemToEntityConfig.java:12`，默认 30，item_to_item / item_to_mob / item_to_xp_orb 继承）、`radius_limit`（`ItemToBlockConfig.java:23`，默认 6）、`block_of_item`(:25)、`block_place_shape`(:27)、`xp_per_item`（`ItemToExpOrbConfig.java:17`，默认 1）、`entity_age`（`ItemToMobConfig.java:20`）、`side_effect`（`ItemToWorldEffectConfig.java:22`）、`visual_only`(:27)、`weather_duration_ticks`(:31)、`is_thundering`(:34)、`explosion_power`(:38)、`explosion_fire`(:41)、`explosion_direction_type`(:44)、`arrow_pickup_status`(:48)、`arrow_potion_effects`(:51)。
- 无 `schema_version`、无迁移分支（`config/handler/BaseConfigHandler.java` 只做 Gson 列表读写 + `shouldProcess()` 过滤）。

### 3.2 条件与轮数（旧模型的核心算法）
- 旧条件全部是 **AND**：`condition/ConditionCheckerUtil.java:42-55` 的 `combineAll` 逐项检查、任一失败即整条不成立；没有 OR，也没有取反。条件来源为 `dimension` / `need_outdoor` / `surrounding_blocks` / `catalyst_items` / `inner_fluid`（`BaseConversionConfig.java:216` `getConditionChecker()`）。
- 轮数算法：`BaseConversionConfig.java:253` `computeActualRounds`，取三轮最小值——起始轮数（堆叠数 / `source_multiple`）、催化剂可支持轮数（:259 调 `catalystItems.getMaxConvertibleRounds`，`CatalystItems.java:164`）、结果容量轮数（子类的 `getResultCapacityInRounds`）。
- 一次转化实际消耗源物品 `rounds × source_multiple`，并一次性产出 `rounds × result_multiple` 份结果。
- 催化剂语义（`CatalystItems.java`）：`catalyst_items`(:30) 每个条目带自己的 `count`(:216-219)；判定要求**每个条目分别满足**（:64 `checkCondition` 遍历并取本地数量快照）；消耗 `consume_catalyst`(:33) 为真时按「每轮 `entry.count()` × 起始物品数」扣（`CatalystItems.java` 内 `consumeFromLevel`），按标签展开顺序依次扣，范围是触发实体所在 **1×1×1** 格内的掉落物。
- 流体语义（`InnerFluid.java`）：`inner_fluid`(:27)、`require_source`(:29)、`consume_fluid`(:31)；消耗时 `require_source` 为真且非源方块流体则不消耗，含水方块只把 `WATERLOGGED` 置 false（保留方块），其余含流体方块整块置空气（:65 `consumeFluidFromLevel`）。

### 3.3 世界现象（`config/WorldEffectType.java`）
- 五种：`RAIN`(:21)、`CLEAR`(:38)、`LIGHTNING`(:55)、`EXPLOSION`(:69)、`ARROW_RAIN`(:88)。
- RAIN / CLEAR 有**隐式前置条件**：维度没有天空光、或天气状态与目标不一致时**静默 return，不执行也不报错**（:21-54 的 lambda 内 `return`）。
- 现象参数由 `WorldEffectType.SideEffectConfig` 提供，默认值：`getWeatherDurationTicks()=6000`(:144)、爆炸 `power=1`、`fire=false`、`DirectionType.FLAT`、箭矢 `Pickup.DISALLOWED`、`isVisualOnly()=false`（:144-159）。
- 轮数展开：`ItemToWorldEffectConfig.performConversion` 把 `rounds` 作为 `count` 传给执行器（`worldEffect.getExecutor().execute(..., rounds, ...)`）；天气类固定 1 轮。因此 LIGHTNING / EXPLOSION / ARROW_RAIN 的「数量」= 轮数，并伴随可配置的间隔字段（`lightningIntervalTicks` / `explosionIntervalTicks` / `arrowIntervalTicks`）。
- 方块放置（`ItemToBlockConfig.java:80-110`）：每次触发放置 `rounds × result_multiple` 个方块，间隔 `Constants.blockPlaceIntervalTicks`，形状取 `BlockPlaceShape`；该枚举在 `server/task/PlaceBlockTask.java` 内，四值 `SQUARE` / `CIRCLE` / `CUBE` / `SPHERE`（各自 三维/欧氏 两个标志位）。
- 标签：`util/IdValidator.java` 说明 **item 与 block 支持 #tag**（:32-45、:52-56），但 **result 不支持 tag**（:47 注释「不支持 tag」）；标签展开在 `util/TagResolver.java:42-44` 用 `registry.getTag`。

## 4. §13.2 五个重点检查项逐项映射

判定用三档：**可简单可靠映射** / **需特判** / **无法保留**。新模型字段路径按最终规则 JSON 写（条件树里除根以外均为叶子：`{"op":"leaf","condition":{...}}`）。

### 4.1 催化剂（全部满足 / 各自数量 / 轮数 / 消耗）——需特判

| 旧行为（证据） | 新模型对应 | 判定 |
| --- | --- | --- |
| `catalyst_items` 每项独立 `count`，判定「每项分别满足」（`CatalystItems.java:64`、:216-219） | `conditions` 下 `catalyst_present` 只有单一 `count`（`CatalystPresentCondition.java:21-24`、:26） | 需特判：多条目只能拆成多个 `all_of` 叶子，且各项 count 必须相同才等价 |
| 命中判定按「逐条目分别满足」 | 新判定是「命中 `items` 中任意一项的**总数量** ≥ `count`」（`CatalystPresentEvaluator.java:28-44`，聚合 `total[0]+=getCount()`） | 需特判：多条目从「分别满足」变成「合计数量」，语义不等价 |
| 消耗按每轮「`entry.count()` × 起始物品数」，各条目按比例被吃 | `consume_catalyst` 只按总量 `count × rounds` 由近及远扣（`ConsumeCatalystExecutor.java:41-62`） | 需特判：各条目的消耗量不守恒 |
| 范围：判定与消耗都在同格 1×1×1 | 判定仍是 1×1×1（`CatalystPresentEvaluator.java:34` `unitCubeFromLowerCorner`）；消耗是 `radius`（默认需显式给 1） | 可对齐（转换时写 `radius: 1`） |
| 轮数受催化剂存量压缩（`BaseConversionConfig.java:253-262`） | 新轮数只看源物品；催化剂不足只 warn（`ConsumeCatalystExecutor.java:64-66`） | 无法保留（见 4.3 差异 1） |

### 4.2 流体与在场 / 消耗 / 含水方块——可简单可靠映射

| 旧行为（证据） | 新模型对应 | 判定 |
| --- | --- | --- |
| `inner_fluid` + `require_source` 判定在场（`InnerFluidConditionChecker.java:59`） | 条件 `fluid_present`：`{"type":"...:fluid_present","fluid":"...","require_source":true}` | 可简单可靠映射 |
| `consume_fluid` 为真才消耗；每轮 1 格 | 效果 `consume_fluid`（`ConsumeFluidEffect.java:27-32`），每轮 1 格（`ConsumeFluidExecutor.java:44-51`） | 可简单可靠映射 |
| 含水方块只移除 `WATERLOGGED`，其余含流体方块置空气（`InnerFluid.java:65`） | 同一分支逐字保留在 `ConsumeFluidExecutor.java:63-70` | 可简单可靠映射 |
| `inner_fluid` 为空 = 不限制流体 | `fluid` 可空 = 任意流体（`ConsumeFluidEffect.java:28`） | 可简单可靠映射 |
| `require_source` 表示「要求是源方块流体」 | 同名 `require_source`（`ConsumeFluidExecutor.java:60`） | 可简单可靠映射 |

注：消耗格数在旧实现里也通常只有 1 格（同一位置同 tick 只能消耗一次），差异主要来自轮数含义（见 4.3）。

### 4.3 源/结果倍率、余量、容量上限、result_limit 与堆叠——部分可映射 + 两处需特判

| 旧行为（证据） | 新模型对应 | 判定 |
| --- | --- | --- |
| `source_multiple` = 每轮消耗源物品数（`BaseConversionConfig.java:61`） | 效果 `consume_source` 的 `count`（每轮消耗量）；新 `rounds = 堆叠数 / 每轮消耗量`（`ConversionRuntime.java:362-366`） | 可简单可靠映射 |
| `result_multiple` = 每轮结果份数（:65）；总结果 = `rounds × result_multiple` | `spawn_item` / `spawn_entity` / `place_block` 的 `count`，执行器做 `count × rounds`（`SpawnItemExecutor.java:36-37`、`SpawnEntityExecutor.java:37`、`PlaceBlockExecutor.java:75`） | 可简单可靠映射 |
| `result_limit`（默认 30）+ 邻近半径 6（`BaseItemToEntityConfig.java:12`、`BaseConversionConfig` 的 `MAX_RADIUS=6`） | `limit` + `radius`（`SpawnItemExecutor.java:48-71`：统计半径内同类产物总量并按 `limit` 收敛；未给 `radius` 时默认 6） | 可简单可靠映射 |
| **轮数被三重压缩**：`rounds = min(起始轮数, 催化剂轮数, 结果容量轮数)`（`BaseConversionConfig.java:253-262`） | 新轮数**只**按源物品算；催化剂不足只 warn，结果容量只在产出侧收敛 | **需特判**（差异 1） |
| 经验球总量 = `rounds × result_multiple × xp_per_item`（`ItemToExpOrbConfig.java:44` 起） | `spawn_xp.amount` 配 `per_source_item`：乘以「覆盖源物品数」或 rounds（`SpawnXpExecutor.java:24`） | **无法保留**（差异 2） |

- 差异 1（需特判，但值得注意）：旧模型里催化剂或结果容量不足会**减少源物品的总消耗量**（因为 rounds 变小）；新模型固定按可用源物品算 rounds，源物品足量被扣，只在催化剂侧少扣（warn）或产出侧收敛。转换器无法在不改变用户数据语义的前提下消除该差异；能做的只有照实写出新规则并声明行为差异。
- 差异 2（无法保留）：要让 `amount × covered = rounds × result_multiple × xp_per_item` 恒成立，需要 `amount = xp_per_item × result_multiple / source_multiple`；除 `source_multiple = result_multiple = 1` 外一般不成立（非整数或需要把倍率挪到别的字段），因此经验球规则不能保证等价换算。

## 5. 「无法保留 / 停止并报告」清单

以下条目在新模型中**没有等价承载**，属于结构性缺失；任何转换器遇到它们只能拒绝或降级，因此本评估建议不做转换器：

1. **爆炸方向** `explosion_direction_type`（默认 FLAT）——新 `explosion` 无方向字段。
2. **闪电纯视觉** `side_effect=lightning` + `visual_only=true`——新 `lightning` 无 `visual_only`。
3. **世界现象的时间展开参数**：`lightningIntervalTicks` / `explosionIntervalTicks` / `arrowIntervalTicks`（新实现硬编码 8 / 无 / 2），以及 **EXPLOSION 的 `count`（=轮数）**——新 `explosion` 每次触发只炸一次。
4. **方块形状 `CUBE` / `SPHERE`**（3D 放置）——新 `shape` 只有 `SQUARE/CIRCLE/CROSS`。
5. **经验球倍率组合** `rounds × result_multiple × xp_per_item`——新的 `amount × (per_source_item ? 覆盖源物品数 : rounds)` 无法在 `source_multiple ≠ 1` 或 `result_multiple ≠ 1` 时等价换算。
6. **多条目催化剂的「逐条目数量 + 分别满足 + 按量守恒消耗」**——新 `catalyst_present` 只有单一 `count` 且按合计数量判定，`consume_catalyst` 按总量由近及远扣。
7. **旧轮数压缩**：催化剂存量与结果容量会减少源物品总消耗量（`computeActualRounds`），新模型轮数只按源物品。

其余旧字段（item/result、无 tag 的 result、conversion_time、need_outdoor、dimension、surrounding_blocks、radius_limit、block_of_item、catalyst/fluid 的单条目用法、天气四种参数、箭矢 pickup 与药水、SQUARE/CIRCLE 形状）都存在直接或近似对应，单独看都是可映射的。

## 6. 方案对比与选择理由

- 方案 A（重写转换器）需要逐项特判 §5 的 7 类情况，其中 1-4 项**新模型无字段**：转换器只能「拒绝这些规则」或「静默降级」，与 §13.2「不悄悄丢字段、有歧义就停止并报告」冲突；5-7 项需要改写语义并给出行为差异声明。转换器还要长期携带旧语义（`result_multiple`、`side_effect` 统一文件、运行期条件检查器、`BlockPlaceShape` 四值），会持续拖累新设计。
- 方案 B（破坏性更新）与 §13.2「不为迎合旧数据改最终架构」「中间开发版本无需维护读兼容」一致；旧 JSON 原样保留在磁盘，用户按更新说明手工重建（编辑器已能覆盖全部字段，见 P5 复核报告），并可用旧→新对照表逐条翻译。
- **选择 B。**
