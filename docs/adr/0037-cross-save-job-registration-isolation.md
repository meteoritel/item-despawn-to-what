# ADR-0037：跨存档后台作业登记的隔离语义

- 状态：已实施；覆盖层作业与停服时序见 [edit-protocol.md](../dev/backend/modules/edit-protocol.md)。
- 相关决策：[ADR-0019](0019-exclusive-edit-session-and-target-lock.md)（编辑会话与目标锁的独占语义，本 ADR 只管文件作业的登记范围）。

## 背景

覆盖层文件的解析与读写统一由进程内唯一后台线程承担，其待执行队列有固定上限。作业登记此前是进程级静态集合：目的是「旧存档的文件工作没有真正退出前，不启动下一存档」，避免两轮规则文件写入交错。

但进程级登记存在两个问题：同一进程内先后启动多个服务端（单人世界切换存档）属于正常路径，旧一轮的残留登记会让新存档在加载规则前被永久拒绝启动；停服等待的 30 秒期限只用于放弃等待，登记本身仍然保留，于是「作业可能早已结束」与「作业确实还在写盘」在后续存档看来无法区分。

## 决策

1. **作业登记按实例隔离**：每个覆盖层存储实例持有自己的在途作业集合，另有一个进程级集合登记仍然存活的存储实例。
2. **到期限放弃登记并解除阻塞**：停服在期限内等待在途作业结束；到期限仍未结束时，该实例放弃登记并解除对后续存档的阻塞，同时记录 ERROR——作业可能仍在写盘。
3. **只有仍有在途作业的实例才阻塞启动**：空实例一律放行，已完成的旧存档不再影响下一次启动。
4. **进程级约束不变**：文件 I/O 仍由唯一后台线程执行，待执行队列上限仍是进程级的。

## 考虑过的替代方案

- **保留进程级登记与超时保留（原状）**：旧存档的作业会永久阻塞新存档，切档即触发，且阻塞条件与真实执行状态脱钩。否决。
- **超时后强制中断后台线程**：底层 I/O 不保证响应中断，强杀可能留下半写的规则文件与备份，损坏代价高于短暂阻塞。否决。
- **停服不做任何等待直接放行**：连「作业已经结束」这一最常见情形都不再确认，等于把可能的写盘立刻暴露给下一存档。否决。

## 后果

- 切换存档不再因上一轮残留作业永久阻塞；完成过的旧存档对后续启动完全无影响。
- 停止语义相应变弱：到期限后只保证不再阻塞，不保证文件工作已结束；唯一线索是日志中的 ERROR，且该作业仍占用唯一后台线程。
- 新增跨存档共享状态时必须显式区分「实例级」与「进程级」，不能再用静态登记承载实例生命周期。
