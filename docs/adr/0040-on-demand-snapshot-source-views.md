# ADR-0040：快照按需下发来源视图

- 状态：已实施。
- 相关决策：部分修订 [ADR-0020](0020-source-catalog-and-overlay-control-entries.md) 第 1 条中「快照条目承载三视图」的约束；来源目录仍保留基底、覆盖与控制条目三份原始内容。协议版本化与回执状态码沿用 [ADR-0019](0019-exclusive-edit-session-and-target-lock.md)。

## 背景

列表页只用 `effective`；`base` 与 `overlay` 仅在编辑页的「恢复原始版本」与来源对照时需要。若快照为每条规则携带三份 JSON，规则数量增长时快照字节、分片数、客户端解析与深拷贝都会成倍增长，而列表首屏只消费其中一份。

## 决策

1. **列表快照只带生效视图**：条目携带 `effective`、来源、状态、可编辑标记、问题清单，以及 `hasBase`/`hasOverlay` 存在标记。
2. **来源视图按需请求**：编辑页打开某条规则时，按规则标识请求该规则的 `base` 与 `overlay`，并随附来源元数据（所属层、数据包 id、文件路径）；列表页不发起该类请求。
3. **客户端短期缓存**：缓存最近 8 条来源视图，命中不重复请求；缓存随会话结束清空。
4. **失败降级**：请求沿用既有会话校验、请求标识幂等与超时丢弃；失败或超时时来源对照降级为不可用并提示，规则编辑与保存不受影响；来源视图取回前「恢复原始版本」不可用。
5. **协议版本递增**：快照条目结构变更属于不兼容变更，客户端在握手阶段按版本拒绝，不做双版本兼容。
6. **快照解析只持有生效视图**：客户端条目只持有生效视图，避免同一份内容在解析、模型与展示层反复深拷贝。

## 考虑过的替代方案

- **保留三视图**：列表页承担两份额外内容的传输与解析成本，且随规则数量线性放大。否决。
- **`base` 与 `effective` 相同时省略**：不新增载荷，但平均仍带 1.5~2 份内容，且需要逐条比较才能判定是否省略。否决。
- **只裁掉 `overlay`**：`overlay` 只在部分规则上存在，主要冗余在 `base≈effective`，收益最小。否决。
- **改小分片或提高每 tick 投递量**：只改善投递节拍，不减少字节与解析量。否决。
- **双版本兼容窗口**：结构变更是破坏性的，模组双端同版本发布，兼容窗口只增加测试面。否决。

## 后果

- 编辑页需要来源视图加载态、缓存与失败兜底；「恢复原始版本」在来源视图取回前不可用。
- `RuleSnapshotEntry`、快照装配、客户端解析、草稿视图与编辑页数据加载都按「生效视图常驻、来源视图按需」分工。
- 条目只带生效视图后，快照与分片上限可重新评估，但不作为本决策的前置条件。
