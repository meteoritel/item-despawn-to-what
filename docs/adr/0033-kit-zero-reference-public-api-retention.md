# ADR-0033：kit 零引用公开类的保留口径

- 状态：已接受；kit 依赖边界与公开面见 [UI kit 模块文档](../modules/ui-kit.md)。
- 依据：kit 的库化目标，以及用户对「kit 内零引用公开类去留」的答复。

## 背景

[ADR-0030](0030-ui-kit-as-standalone-library-api.md) 决策 3 要求：kit 零引用的公开类不留悬空——确认为对外公开 API 则登记进公开面，否则删除；该 ADR 已否决「对零引用公开类不表态」。通用能力归位（见 ADR-0030 决策 2）之后，kit 内仍有一批除 kit 自身与装配示例外零引用的公开类，覆盖预留的面板、导航、布局与输入原语。它们的共同点是「面向通用宿主或用于装配演示」，但当前没有生产消费点；若不说明用途，引用计数会被误当作唯一去留依据。

## 决策

1. **零引用公开类若属 kit 预留面或装配示例，保留并登记**：登记到公开面分组与已知限制即可，不视为悬空。
2. **登记必须说明用途与当前无生产引用**：每项注明能力用途，并写明「当前无生产引用」，使拆库时可以逐项裁决。
3. **预留面与示例仍受 kit 边界约束**：不含本模组业务、文案与语言 key，依赖边界脚本照常校验。

## 考虑过的替代方案

- **全部删除**：会丢掉已按通用 API 冻结的预留面，其它宿主仍要重新实现。
- **不表态、保持沉默**：公开面无法核查，与 ADR-0030 已否决的方案重复。
- **从公开面移出并标为内部**：这些类本就是宿主可用能力，降级为内部会误导接入方，也与 kit 作为库 API 的定位冲突。

## 后果

- 引用计数不再作为删留的唯一依据；保留项必须在公开面上逐项登记。
- kit 公开面发生变化时需要同步更新登记，边界脚本仍是唯一强制校验。
- 拆库时按登记清单逐项裁决「随库发布 / 转为内部 / 删除」。
