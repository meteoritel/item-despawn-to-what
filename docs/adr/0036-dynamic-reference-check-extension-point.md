# ADR-0036：动态引用校验作为参数对象上的扩展点

- 状态：已实施；校验分层见[错误与校验](../api/errors.md)。
- 相关决策：[ADR-0013](0013-dfu-codec-and-flat-type-dispatch.md)（扁平字段按类型分发，参数对象与类型标识同层）。

## 背景

部分引用的合法性只有拿到服务端世界与注册表才能判定：战利品表效果、维度条件、群系条件都属于这一类，统称动态引用。把这类判定写在核心校验器里，每新增一个带动态引用的类型都要改校验器，扩展点无法由类型作者自己完成；而把扩展点放在类型的能力定义上，又会牵动校验入口的签名与散落在加载、保存、快照与提交校验各处的调用点。

## 决策

1. **扩展点落在参数对象上**：参数对象可选实现一个默认空实现的校验接口，核心校验器按接口分派。
2. **上下文携带判定所需的一切**：服务端引用、问题累积器与字段路径；来源作用域由能派生来源继承子收集器的累积器统一处理，不需要校验器逐处传参。
3. **核心校验器只遍历与汇总**：它负责走到顶层效果与候选结果内效果，不含任何具体类型的判定逻辑。
4. **内置类型在各自参数对象上实现**：战利品表效果、维度条件与群系条件按同一方式接入。

## 考虑过的替代方案

- **把扩展方法放到类型定义上**：需要改动校验入口签名或增加重载，牵动加载、保存、快照与提交校验的调用点与注册表接口，而这些调用点的语义并不因此变好。否决（本轮的主要取舍理由）。
- **校验器内继续按类型枚举分支**：每新增一类动态引用都要改核心校验器，第三方类型无法自行接入，扩展点名存实亡。否决。
- **用「类型 → 校验器」注册表反查**：参数对象已经持有判定所需的参数，再引入一层映射既增加登记负担，也与扁平分发的参数结构脱节。否决。

## 后果

- 新增带动态引用的类型只需在参数对象上实现接口，核心校验器与加载、保存、快照、提交校验的调用点保持不变。
- 代价是同一类型的校验逻辑分处两处：参数结构校验与类型定义一侧，动态引用校验与参数对象一侧；文档需按此分工描述。
- 问题来源的继承由累积器的来源作用域统一保证，校验实现不自行拼接来源。
