# ADR-0038：转化结算的单一状态提交点与库存所有权标记

- 状态：已实施；结算与账本见 [conversion-runtime.md](../dev/backend/modules/conversion-runtime.md)。
- 相关决策：[ADR-0023](0023-triggers-fixed-cost-and-complete-group-settlement.md)（完整组结算与固定成本语义不变，本 ADR 只收口结算状态的写入路径）。

## 背景

一次转化结算有多条出口：正常完成、显式中止、预算耗尽提前让出、为交付产物而让出。每条出口都要把「这一堆源物品现在归谁、还剩多少待交付」写进账本，而源堆叠在被扣走后到交付完成前仍可能存在于世界中。

此前的做法是每条出口各自写账本，于是「库存是否仍归本次结算持有」只存在于各出口的隐含判断里：漏写会让账本与真实持有不一致，重复登记会把已交付数量再算一次待交付。

## 决策

1. **结算状态只有一个提交点**：所有出口统一经同一提交方法落盘，出口本身不再各自写账本。
2. **显式的库存所有权标记**：标记表示源堆叠是否仍归本次结算持有；持有则提交时同步待交付数量并登记，不持有则只落盘终态；显式中止先清除标记，再走同一提交点。
3. **同一刻内的容量测量复用**：同一刻内同一候选只查一次世界并复用结果，每步开始清空，避免跨刻复用造成高估。

## 考虑过的替代方案

- **每条出口各自写账本（原状）**：出口数量随业务增长，任何一处遗漏都表现为账实不符，且难以在评审时穷举。否决。
- **用「源实体是否仍存在」代替所有权标记**：源实体在交付完成前通常仍存在于世界，无法区分「刚从源堆叠扣走」与「已经交付完毕」，判定不成立。否决。
- **为结算引入通用事务框架**：结算语义单一（整堆扣减、按组支付、失败返还），引入通用事务会带来远超收益的复杂度与回归面。否决。

## 后果

- 账本写入路径唯一，所有权语义显式可见；新增出口必须走同一提交点，否则视为缺陷。
- 提交点承担「同步待交付数量 + 登记」的固定顺序，任何一方语义变化都要在此处一并调整。
- 容量测量必须按刻复用而非跨刻缓存，跨刻复用不被允许。
