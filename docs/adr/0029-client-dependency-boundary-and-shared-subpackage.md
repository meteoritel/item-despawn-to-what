# ADR-0029：客户端依赖边界与中立共享子包

- 状态：已接受；界面层可用只读 DTO 的表述见[客户端层文档](../dev/layers/client.md) §1/§2。
- 依据：客户端 UI 分层审查的实测结论，以及用户对「传输载荷类型」范围与反向依赖两项待裁决问题的答复。

## 背景

[客户端层文档](../dev/layers/client.md) 规定层内单向 `client/net`（协议）→ `client/edit`（草稿与注册表）→ `client/ui`（界面），并写明「界面层不得直接接触传输载荷类型」「只读工作区视图不暴露任何传输载荷类型」。实测与表述不一致：界面层多个文件直接使用 `core.network.protocol` 的只读 DTO，承担隔离职责的只读工作区视图本身也导出这些类型；同时 `client/edit` 反向依赖 `client/ui`（草稿与撤销栈持有表单校验问题类型、业务节点实现 kit 树接口），`ui/screen` 与 `ui/screen/form` 双向依赖并存在类级相互引用，界面层还直接使用 Gson。

差异使契约失去约束力：新增界面能力可以各自解释「现状允许」，协议 DTO 增删会穿透界面，草稿层无法脱离 UI 包使用。因此需要先裁决「传输载荷类型」的范围，再固定三处依赖的方向。

## 决策

1. **传输载荷类型只指传输通道类型**：传输通道由 `client/net` 收敛，界面层不接触；`core.network.protocol` 的只读 DTO（快照与条目、问题、目录、保存状态）视为客户端可用契约，界面层可直接使用。界面层仍不得直接构造或发送上行载荷。
2. **`client/edit` 不反向依赖 `client/ui`**：草稿与撤销栈持有的校验问题类型下沉到 `client/edit`；业务节点不再实现 kit 的树接口，适配留在宿主侧。
3. **`ui/screen` 与 `ui/screen/form` 不互为依赖**：两者共享的纯值与展示类型放入中立子包，两个子包只依赖中立子包与 kit／widget。
4. **界面层不直接使用 Gson**：JSON 解析与构造收敛到 `client/edit`，界面只消费模型或转换结果。

## 考虑过的替代方案

- **维持「界面层不接触任何协议类型」，在 `client/edit` 增加视图模型层**（快照、问题、目录各一份镜像类型）：隔离更彻底，但每个协议 DTO 都要维护镜像与转换，协议演进须两处同改；只读工作区视图已承担传输通道隔离，收益与外扩成本不成比例。
- **承认 `ui/screen` 与 `ui/screen/form` 同层双向**：类级环不消除，改动影响面仍无法判断，两个子包也不能独立测试。
- **把 kit 登记为可被 `client/edit` 依赖的公共边界**：草稿层与 UI 基础设施耦合，kit 独立发布时须连带发布树适配契约，与 kit 的库化目标冲突。
- **保留界面层 Gson 用法**：解析与布局继续交织，结构变化直接穿透界面。

## 后果

- [客户端层文档](../dev/layers/client.md) §1/§2 按本决策改写：界面层可直接使用 `core.network.protocol` 的只读 DTO，但不得直接构造上行载荷。
- 传输通道仍由 `client/net` 收敛，端隔离与平台隔离不变。
- `ui/screen/form` 不再依赖 `ui/screen`，`client/edit` 不再依赖 `client/ui`，界面层不再出现 Gson 用法。
- 契约细节在对应实现落地后由 `docs/dev` 同步；本 ADR 不复述类清单。
