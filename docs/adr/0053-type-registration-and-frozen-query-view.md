# ADR-0053：注册窗口由装配所有者关闭，消费方持有冻结查询视图

- 状态：已实施。
- 相关决策：[ADR-0013](0013-dfu-codec-and-flat-type-dispatch.md)（注册表分发）、[ADR-0049](0049-single-parameter-declaration.md)（类型声明）。

## 背景

内置登记、第三方 provider 与运行期查表具有不同生命周期。provider 需要在开放窗口内登记或查询类型，装配所有者决定封口时机，加载与运行期只需要稳定查询。让所有调用方共享注册和冻结能力，会使装配次序与只读约定依赖调用方自觉。

## 决策

- `TypeRegistry` 只表达查询；`TypeRegistrar` 在查询上增加注册能力，供内置登记和 SPI provider 使用。
- `SimpleTypeRegistry` 是装配期 builder，装配所有者持有它并负责 freeze；冻结返回独立、保序、不可变的查询视图，重复冻结返回同一视图。
- `BuiltinTypeRegistries` 归 `core/type`，统一装配内置与 SPI 类型。条件冻结后构建表达式 Codec，再装配并冻结效果；两侧使用同一流程。
- 旧注册句柄继续受封口状态约束，已发布视图只包含冻结时的定义。注册与冻结属于同一装配线程，冻结查询视图可跨线程读取。

## 考虑过的替代方案

- 将 freeze 放进 provider 使用的接口：把关闭其他 provider 注册窗口的能力交给了参与者。
- 返回同一个可变 builder、仅靠变量类型约定只读：查询对象仍暴露实现侧的注册能力，生命周期责任难以分辨。
- 在加载服务与内置工厂分别构建注册表：装配顺序和冻结位置形成多个维护点。

## 后果

- 装配能力和运行期查询能力由返回类型区分，具体 builder 留在类型系统装配点。
- Java 扩展使用 `TypeRegistrar` 注册类型，并适配 typed 参数绑定后重新编译。规则 JSON、编辑协议与类型标识保持原有形态。
- 具体实现、扩展步骤和校验入口见[类型系统](../modules/type-system.md)。
